# 2. JPA entity as the domain model

- Date: 2026-10-09
- Status: Accepted

## Context

The domain is small (clients, menu, orders, the client account) and the project
is built in irregular, limited time. The persistence layer is Spring Data JPA
with Hibernate. A strict Clean or hexagonal layout would separate a pure domain
model from the persistence entity and map between the two.

## Decision

We will use one class per aggregate that is both the domain model and the JPA
entity, and that carries its own invariants.

- Entities expose behavior, not setters: a private constructor, a static factory
  method (`create`), and methods that change state (`update`, `deactivate`,
  `activate`). Validation and normalization live inside the class, so there is
  no way to build or change an entity into an invalid state.
- Only `@Getter` from Lombok. `@Data`, generated `equals`/`hashCode` and
  `toString` are avoided on entities.
- Hibernate requirements are met explicitly: a `protected` no-argument
  constructor, and classes and fields that are not `final`.
- Identifiers are generated by Hibernate and are null until the first save.
- Ports are introduced only at real boundaries where more than one
  implementation is plausible, such as the client account interface (ADR-0001)
  and the payment gateway. Repositories are Spring Data interfaces.
- Business rules live in entities and services, never in controllers.

## Alternatives considered

1. **Separate domain model and persistence entity, with mappers.** This keeps
   the domain free of JPA annotations and makes it testable without any
   framework on the classpath. It was not chosen because it roughly doubles the
   number of classes per aggregate, adds mappers that carry no business value,
   and gives up Hibernate's dirty checking, since every update becomes load,
   map, save. For a domain this size the cost outweighs the benefit.
2. **Anemic entities with all rules in services.** Rejected: invariants would be
   scattered and an invalid entity could be built from anywhere.

## Consequences

Positive:

- Less code and no mapping layer; Hibernate features work as designed.
- Invariants are enforced in one place, and can still be unit tested without
  Spring, since they are plain methods.

Negative:

- The domain model is coupled to JPA annotations and to Hibernate's
  constraints (non-final classes, a no-argument constructor).
- Moving to a strict separation later is a refactor that touches every
  aggregate, so the decision should be revisited if the domain grows
  significantly in complexity.
